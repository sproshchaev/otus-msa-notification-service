# 0008. Заявки живут в одной базе, идентификатор заявки несёт виртуальный шард

- **Status:** Accepted
- **Date:** 2026-10-01
- **Deciders:** Сергей Прощаев

## Context

Таблица заявок и история статусов — единственные наборы данных сервиса, которые растут: около
трёх миллионов заявок и пятнадцати миллионов строк статусов в год, в пик рассылки порядка
300 записей в секунду. Разбор по [решению о данных](../21-data-scaling.md#шаг-2-шардировать-или-нет)
показал, что одна база PostgreSQL держит это с большим запасом, и шарды сегодня добавили бы
только издержки.

Там же всплыла проблема, которая от шардов не зависит. Идентификатор заявки — случайный UUID.
Два главных запроса к данным — история по получателю и статус по идентификатору заявки. Если
когда-нибудь шардировать по `recipient_id`, второй запрос, самый частый, уйдёт во все шарды:
по случайному идентификатору шард не вычислить. Менять формат идентификатора потом означает
миграцию всех заявок и всех клиентов, которые его хранят.

Рассматривал три варианта:

1. шардировать сейчас по hash от `recipient_id`;
2. оставить одну базу и случайный UUID, вопрос отложить;
3. оставить одну базу, а в идентификатор заявки заложить номер виртуального шарда.

## Decision

Заявки и история статусов остаются **в одной базе** с секционированием по месяцу. Шарды
возвращаются в повестку по числу: запись в пик устойчиво выше 3 000 в секунду или горячие
секции за год больше 500 ГБ.

Идентификатор заявки **несёт номер виртуального шарда**: `hash(recipient_id) mod 1024`
плюс порядковая часть. Карта «виртуальный шард → узел» будет жить в клиентской библиотеке
сервиса; сегодня все 1024 виртуальных шарда отображаются на один узел.

## Consequences

**Что выигрываем.** Сегодня — простота одной базы: транзакция на заявку, статус и ключ
идемпотентности остаётся локальной, отчёты не обходят узлы. Завтра — шардирование без миграции
идентификаторов: и история получателя, и статус по идентификатору попадают в один шард, а переезд
идёт целыми виртуальными шардами.

**Чем платим.** Идентификатор перестаёт быть непрозрачным: по нему можно понять номер
виртуального шарда, и клиентам надо прямо запретить разбирать его структуру. Генерация
идентификатора требует `recipient_id` в момент приёма — у нас он там есть всегда. Число
виртуальных шардов зафиксировано на годы: 1024 хватает до сотни узлов, дальше понадобится
пересчёт.

**Что отвергли.** Шарды сейчас — издержки без выгоды: каждый отчёт поддержки превратился бы
в обход узлов, а нагрузка не упирается ни в запись, ни в объём. Отложить вопрос целиком —
дешевле сегодня и заметно дороже в день, когда он встанет: к тому моменту случайные
идентификаторы разойдутся по клиентам и логам.
